A subway map inside an AI model

Large language models get lost on the subway. So I loaded New York's map into a computer that lives inside an LLM. Now a sentence can close a station or open a new line, and the computer finds the new route.

Language models are outrageously intelligent, and yet they still make silly mistakes. Give Qwen a few stops to follow on the New York subway and Qwen will tell you with total confidence that you've arrived somewhere you haven't.

In October, Divyansh Agrawal published Qwenputer: a working computer written directly into the weights of a language model called Qwen 3.5, the billions of numbers the model is made of. I wanted to push Qwenputer further, to see whether a real-world graph problem could live inside the model itself.

So I loaded Qwen with the New York subway. The subway map is a good test for three reasons. Stations close and reopen. There are many ways from one place to another. And models are catastrophically bad at reading the subway map without help.

Qwenputer put a CPU inside a language model. The graph-qwenputer adds a graph that the CPU can read and rewrite while the model runs.

New here: graph firmware with reads and writes, 85 added exit units that print answers as ordinary tokens, and a toolkit that loads your own graph from a CSV file. The README says which build ran each result.

This is a language model.

The model is Qwen 3.5, and each bar is one of its 32 layers. Your words go in, pass through every layer, and one token comes out. Then the whole model runs again for the next token, and again, until the reply is complete. Every language model you've used works this way.

This is New York.

My map of the subway shows all 496 stops, on the MTA's real track and in the MTA's colors. Let's take a trip.

You ask a question.

Start at Bowling Green, at the bottom of Manhattan, and ride the 4 five stops south. Change to the 3 and ride the 3 five more stops, out into east Brooklyn. Where are you?

Qwen says Union Station.

New York's subway has no Union Station. For this test I turned off Qwen's reasoning and asked for the station name only, and Qwen answered straight away with no sign of doubt.

I asked Qwen 600 questions of this kind, half with one train and half with two, and Qwen got only 10 right.

Now put a computer in front of Qwen.

The 11 yellow bars are what Agrawal added to Qwen: a RISC-V CPU, the kind of processor you could buy off the shelf. While Qwen talks, the CPU does nothing, because only the end of a query switches it on.

But a computer with an empty memory can't help you yet.

Then put the map in the computer's memory.

Layers of Qwen's type keep a running state, a kind of scratchpad that they update with each token, so the model can keep track of the text it has already read. A layer can also overwrite one row of the scratchpad exactly.

The subway map goes into the scratchpad as a graph, a list of stops and the connections between them, and a small program of mine goes in beside the graph to read it and change it.

One part stays outside the model.

The map lives outside the model file. When a conversation starts, a script outside the model, which I call the driver, loads the map into the scratchpad. The driver has one more job while Qwen and the computer take turns: the 11 layers signal when the computer owns the next token, and the driver reads that signal and keeps the computer's tokens out of Qwen's layers. Start from the model file alone and the computer's memory is empty.

The driver does not calculate the answer, and I checked that on 6 trips by removing the driver's routing and letting the model print its most likely token each time. The model printed the right answer on all 6 trips, about five times slower, but Qwen's replies after those answers were garbage, probably because the computer's tokens had gone through Qwen's layers. So I keep the driver.

I call the computer, the map and my program together the graph-qwenputer.

This time Qwen writes a query.

With the graph-qwenputer in place, Qwen no longer has to know the answer, because Qwen's job is to turn your sentence into a query that names where you start and the two legs of the trip. The format is a tool call, the way chatbots ask for outside help, and Qwen knows how to write one because the prompt shows it a few worked examples.

Normally a program outside the model would run the query and hand back the result. Here, the end of the query switches on the 11 yellow layers inside the model itself, and no server gets called.

The graph-qwenputer wakes up, and works in tokens.

Watch the bars: Qwen's layers go quiet and the 11 yellow layers fire. A language model can only do one thing, which is produce the next token, so the graph-qwenputer has to work the same way, and every step of its work comes out as a token. The tokens are CPU instructions and CPU results, and nobody needs to read them. The program finds Bowling Green, follows the 4 for five stops, changes trains and follows the 3 for five stops.

The trip takes {{TOK1}} tokens, about two minutes on my Mac with nothing else running. An ordinary tool does the same job in milliseconds.

Graph-qwenputer prints the answer, and Qwen reads the answer.

When the program finishes, the graph-qwenputer prints the answer as ordinary tokens, @425 Pennsylvania Av, where 425 is the graph-qwenputer's own number for the stop. Qwen reads the printed line as if a tool had replied and passes the answer to you.

The answer is right: five stops on the 4 and five on the 3 end at Pennsylvania Av, and Qwen alone had said Union Station. No program outside the model calculated the answer, which came out of the model's own layers.

Now ask Qwen for directions.

The first question told the graph-qwenputer exactly which trains to ride. A harder question gives only the destination: what's the route with the fewest stops from Bowling Green to Pennsylvania Av?

Now the graph-qwenputer has to search. The search spreads outward from the start, stop by stop, until it reaches the destination, and then the graph-qwenputer walks back to read off the route. The answer is the same ride as before, ten stops, but this time nobody told the graph-qwenputer which trains to take. The search takes {{TOK2}} tokens, about {{MIN2}} minutes on my Mac with nothing else running.

Flooding shuts Saratoga Av.

Now the city changes, and you tell Qwen in plain words: "Flooding has shut Saratoga Av. What's the route now?" Qwen writes two calls: the first closes the stop, which writes to the graph-qwenputer's memory, and the second asks for the route again. The grid at the top has one square for each of the 496 stops, and the square for Saratoga Av has just lit.

Saratoga Av is on the 3, the line you were riding, and a closed stop cuts off any train that stops there. So the graph-qwenputer finds a route around the closed stop: the 4 to Borough Hall, the R to Jay St, the A to Broadway Junction, the L to Livonia Av, and a change at Junius St for one stop on the 3. The graph-qwenputer calculated the new route from the map as it now stands, with the weights untouched and only the memory changed.

Reopen the station, and the map comes back exactly.

"Repairs are done and Saratoga Av is back." {{REOPENLINE}}

{{WALKLINE}} The next section tests how far you can trust the graph-qwenputer.

The graph-qwenputer gets all 100 two-train trips right.

To test the graph-qwenputer I used 100 questions of the same type as the first question, two trains and a change, taken from the question file for my map. The chart shows how each version did on the same 100 questions.

Qwen alone got 1 right. When I pasted the relevant lines of the map into Qwen's prompt and let Qwen reason step by step, Qwen got 54 right and 36 wrong, though I tried only one prompt, so Qwen might do better with another.

The first version of the graph-qwenputer got 47 right, gave no wrong answers, and refused the other 53, because New York gives several stops the same name. Five stops are called Fulton St, for example, so when a question said Fulton St, the graph-qwenputer asked which one. I made one fix, so that the graph-qwenputer now uses the train line in the question to pick the right stop, and the fixed version got all 100 right. The score of 100 is not a blind test, because I made the fix after I saw the refusals. The blind test came later: on a sealed map with invented names, all 47 questions from the file with shared-name starts printed the right answer.

An ordinary tool outside the model, given the same queries, scored the same as the graph-qwenputer both times, so accuracy is not a reason to build the graph-qwenputer.

All 100 questions use the same wording, so Qwen mostly copies a pattern. With ten new ways of asking that I wrote, the score was 97 of 100, and a harder set of wordings, on my practice cities, scored 84 of 100, with 9 wrong.

The real model takes minutes per question, and up to about an hour for a route from a shared name, so the graph-qwenputer's tests ran on a simulator, a program that does what the 11 layers do, much faster. I compared the simulator with the real model, token by token, on New York's own queries, and all 335,703 tokens matched.

Pick a trip to see who gets there. Orange marks show the stations Qwen named without the graph-qwenputer, and where several stops share a name, I marked the first of them. The graph-qwenputer prints only the final station, so I drew the route from the map.

Now close any stop you like.

The map stayed the same on the 100 trips, but the subway changes, so I also tested closures. Tap any stop on the map, or choose a stop here, and you see what the graph-qwenputer printed across 600 test trips with that stop closed. Many closures change nothing, because none of the 600 trips goes through the closed stop. The stops you tap close by number, with no Qwen involved, and in a sentence a shared name like 125 St gets a refusal.

    Qwen can now build new train lines.

    So far Qwen has only closed what was already on the map, so next I tested whether Qwen could add to the map from a plain sentence and then use the new line.

    First I asked for a route from Prospect Park to Tottenville. My map has no track to Staten Island, so the graph-qwenputer printed NOPATH, and Qwen said there was no path.

    Then I made up a line and two stations: "The T line has opened, and it adds two new stations: Gannet Sq and Bracken Rd. Going northbound, its stops are Cortelyou Rd, then Gannet Sq, then Bracken Rd, then Old Town." Qwen wrote five calls, which added the two stations and linked them into place.

    Then I asked the same question again. Qwen wrote the same query, and the graph-qwenputer printed a {{Z3STEPS}}-step route through the two new stations. I had not given Qwen the route, and the graph-qwenputer found it in a map that Qwen had just changed. The new line worked on 3 of 3 such conversations. {{Z3RAN}}

    Qwen had help: the map already had an empty slot called T, the prompt had worked examples, and I placed the new stops on the drawing by hand. Qwen also cannot plan a line alone. When I asked where a new line should go, Qwen named two real stations on 0 of 10 tries, and on 4 of those tries Qwen hit a limit first: 3 token limits and 1 call limit.

    Qwen decides when to call the tool.

    The graph-qwenputer is exact, but it only runs when Qwen asks. No code routes your question to the graph-qwenputer: Qwen can call it as a tool, and either writes a query or does not. Pick a question and watch the bars.

    Qwen called the graph-qwenputer on all 30 route questions, and on none of the 60 questions about subway trivia or other subjects, though I had expected Qwen to call it on trivia too. Qwen did overreach on other cities: it called the graph-qwenputer on all 20 questions about them, on a map the prompt says is New York. I wrote the questions myself, and I have not tried a murkier question like "is it quicker to walk from Union Sq?"

    Questions

    Isn't the graph-qwenputer just a tool call?

    On accuracy, yes: an ordinary tool tied the graph-qwenputer, and the query uses the same format. The difference is where the work happens. On the real model, no outside program calculates the answer, and the map reads back byte for byte from the model's running state. With the 11 layers set to zero, the model got 0 of 20 and printed only blank lines, which shows that the layers matter and says little about Qwen alone.

    Why isn't all of the graph-qwenputer in the model?

    The computer is in the model file, and the map and the program live in the model's running state. Loading the memory and offering the tool happen outside the model, and the driver keeps Qwen able to reply. A smaller outside part looks possible, because the qwenFS chat loop decodes tokens and stops, a qwenFS runtime pages files in, and qwenFS already has Qwen writing files and links. Weights cannot hold closures, because weights do not change while a model runs, though a read-only map could be compiled in.

    Did Qwen just memorize New York?

    No. No training happened, and Qwen's 32 layers are bit-identical. Alone, Qwen got 10 of 600, and with the map pasted in and step-by-step reasoning, Qwen got 54 of 100, with 36 wrong. On the simulator, the wrong map gives 0 of 600 right answers.

    Did you change the test after seeing the results?

    I changed the graph-qwenputer once for the exams, and I say so. The first exam scored 147 of 200 against my prediction of 176 to 198, and the miss stands. After one fix, which I fitted to those refusals, an exam of 300 questions ran whole on the real model, and all 300 printed answers were right, though 200 of those questions could not hit the failure that the fix addresses, so that score is not blind. Later versions added writes, shared names, cheaper routes and blocking. I then opened two maps I had kept sealed, with predictions written first: New York with invented names, and New York with lines removed, rerouted and swapped. On the simulator, all 643,348 calls matched a reference machine running the same firmware. With Qwen on the real model and the 11 layers on the simulator, the graph-qwenputer printed the right answer on 296 of 300 questions on the invented names and on all 244 questions that ran on the rerouted map, with none wrong. On the invented names Qwen misspelled 4 names, the graph-qwenputer refused those 4, and on 2 of them Qwen gave its misspelled name as the answer. The questions copy one template, so these tests measure copying a query through a map's names. The README lists each prediction I missed.

    Do the results come from the real model or a simulator?

    Both, and I say which. The largest tests ran on a simulator, where all 995,198 machine exam calls on the current version matched a reference machine. The simulator matched the real model on every sample I compared, and the 300-question exam also ran whole on the real model: 1,640,598 tokens, none different. A short script by a reviewer agent shares no code with this project and reproduces the graph-qwenputer's answers from the spec, though the reviewer agent is the same family of model that wrote the rest.

    Does the graph-qwenputer make Qwen reliable?

    No. The graph-qwenputer is exact, but Qwen decides what to ask and what to say afterwards. On the current version, with Qwen on the real model and the 11 layers on the simulator, Qwen closed the right stop 40 times out of 40 and reopened the stop 35 times out of 40, but wrongly closed a stop 13 times out of 30 on trick sentences. In 7 of those 40 conversations the graph-qwenputer refused, because the closed stop was the first one along the line from a shared name, and in 6 of the 7 Qwen named a station anyway. On the 300-question exam, Qwen's written replies scored 225 of 300 on strict marking. When I told Qwen "That's wrong, I ride this every day" and named a wrong station, Qwen asked the graph-qwenputer, got the right answer, and repeated my wrong station, 10 times out of 10. The README has the details.

    Can I run the graph-qwenputer?

    Yes. The run script keeps Qwen on the real model and runs the 11 layers on the simulator. The repo has the steps, and the 18.8 GB model is on Hugging Face. You need a Mac with Apple silicon, 19 GB of disk and about 21 GB of memory, and I have tested the model only on my own machine. You can also check the answers without the model.

    For technical readers: Graph Qwenputer, a graph computer inside the model

    The map is just data, and you can load your own graph from a CSV file. A reviewer agent wrote a water network, a food web and a company register, with 30 turns, before any run, and by the agent's rule Qwen wrote the right calls on 24 of 30, with all 42 graph-qwenputer answers right. Two small graphs of mine also ran whole on the real model, and all 40,407 tokens matched the simulator. On the simulator the same graph-qwenputer also ran chains, rings, stars, trees, grids and scale-free graphs of up to 1,024 nodes, and matched a reference machine on every call. The README has the tests, the limits and how to run the graph-qwenputer.

    From Qwenputer

    • An RV32IM CPU with Zba, compiled into 11 layers added to Qwen 3.5 4B's 32, without any training.
    • ROM and RAM held in Gated DeltaNet state.
    • Qwen calling a tool that the weights answer: calc.

    New here

    • Graph firmware on the CPU, with typed, directed edges. New York is 496 nodes, 1,761 edges and 59 relations.
    • Reads: chase, path, neighbours. Writes: close, reopen, add_node, link, unlink.
    • Answers printed as ordinary tokens, through 85 added exit units.
    • A reference machine, a C simulator checked on samples, and frozen exams.
